### Draft (≈1,200 words)

If you've looked up "good Core Web Vitals score" and gotten five different answers, here's why: people conflate three separate things — Lighthouse's lab score, PageSpeed Insights' combined report, and Google's actual real-user pass/fail bar. Only one of those three is what Google uses for Search. This is the technical version, with the thresholds that actually matter.

#### The three metrics, and their real thresholds

Core Web Vitals is three metrics, each with a "good," "needs improvement," and "poor" band:

- **LCP (Largest Contentful Paint)** — time until the largest visible element (usually a hero image or heading) finishes rendering.
  - Good: ≤ 2.5s · Needs improvement: 2.5–4.0s · Poor: > 4.0s
- **INP (Interaction to Next Paint)** — the time from a user's click/tap/keypress to the next frame being painted, measured across the *whole page visit*, not just one interaction.
  - Good: ≤ 200ms · Needs improvement: 200–500ms · Poor: > 500ms
- **CLS (Cumulative Layout Shift)** — how much visible content jumps around unexpectedly while the page loads.
  - Good: ≤ 0.1 · Needs improvement: 0.1–0.25 · Poor: > 0.25

INP replaced FID (First Input Delay) as the official interactivity metric in March 2024. If you're reading an older guide (or an old blog post, or an outdated tool) that talks about FID, the advice is stale — FID only measured the delay before the *first* interaction started processing; INP measures how long interactions take to actually paint a response, across every interaction on the page. INP is a stricter, more honest metric, and a lot of sites that "passed" on FID don't pass on INP.

#### The pass bar nobody mentions: it's the 75th percentile, not an average

Here's the part that trips people up. Google doesn't average your metrics across visitors. A page (or a whole origin) passes Core Web Vitals when **75% of real-user page loads** meet the "good" threshold, for *all three metrics*, over a rolling 28-day window. This data comes from the Chrome User Experience Report (CrUX) — real Chrome users who've opted into usage reporting, not a lab simulation.

That 75th-percentile bar means your slowest quarter of visits doesn't need to pass — but your median and your p50 visit absolutely isn't the number that matters. If your typical visitor is on fast wifi with a new phone but a meaningful chunk of your traffic is on a mid-range Android device on patchy 4G, that slower segment is what decides whether you pass, because it's dragging your p75 toward (or past) the "needs improvement" line.

#### Why your Lighthouse 100 doesn't mean you're passing Core Web Vitals

Lighthouse and the Core Web Vitals pass/fail bar are not the same test, and conflating them is the single most common mistake in this space:

- **Lighthouse is lab data.** It runs once, on one simulated device/network profile, in a clean environment with no other tabs or extensions competing for CPU. It cannot measure INP properly (INP requires real user interaction over a whole session — a lab run that never clicks anything can't produce a real INP number, so Lighthouse approximates with Total Blocking Time instead).
- **CrUX is field data.** It's the aggregate of real Chrome users' real visits, on real devices, on real networks, including the janky ones.
- **A site can score 100 on Lighthouse and still fail Core Web Vitals in Search Console**, because the lab run didn't see the slow 3G visit, the ad-blocker-triggered reflow, or the low-end Android device where your JS bundle takes 400ms just to parse.
- **The reverse also happens:** a site with a mediocre Lighthouse score can pass Core Web Vitals comfortably if its real-world traffic skews toward fast devices and networks.

If your site gets meaningful traffic (CrUX generally needs roughly 1,000+ page loads/month on a given page or origin to report data at all), check the **Core Web Vitals report in Search Console** or pull the origin's CrUX history directly — that's the number Google is actually scoring you on. If you don't have enough traffic for CrUX to populate, Lighthouse/lab data is the best proxy you've got, but treat it as a proxy, not the actual grade.

#### What actually moves each metric (in order of effort-to-payoff)

**LCP:**
1. Preload (not just lazy-load-avoid) your hero image or largest text block's font.
2. Move render-blocking CSS/JS out of the critical path — inline only what's needed above the fold.
3. Use a CDN or at minimum a fast TTFB host; LCP can't be fast if the HTML itself arrives slowly.

**INP:**
1. Break up long JavaScript tasks (anything over 50ms blocking the main thread) — this is usually third-party scripts (analytics, chat widgets, ad tech), not your own code.
2. Debounce or defer non-critical work triggered by user input.
3. Ship less JavaScript overall. This is the least glamorous fix and the most reliable one — frameworks that hydrate large component trees on every interaction tend to struggle here regardless of how well-written the code is.

**CLS:**
1. Set explicit `width`/`height` (or `aspect-ratio`) on every image and embed, so the browser reserves space before the asset loads.
2. Use `font-display: swap` or `optional` with a size-matched fallback font (`size-adjust`) so text doesn't jump when the webfont finishes loading — this is one of the most common unnoticed CLS sources.
3. Never inject content above existing content (banners, cookie notices) without reserving space for it first.

#### The honest summary

"Good" means: LCP ≤ 2.5s, INP ≤ 200ms, CLS ≤ 0.1, at the 75th percentile of your real traffic, over 28 days — not a Lighthouse score, not an average, not a single test run. Everything else is a useful proxy, but it's not the thing Google is actually measuring.
