## Draft guide: What Is a Good Core Web Vitals Score in 2026?

**Suggested title tag:** What Is a Good Core Web Vitals Score in 2026? (LCP, INP, CLS Thresholds) | Site Mechanic
**Suggested meta description:** The real 2026 thresholds for LCP, INP, and CLS, how Google actually scores them (field vs. lab data), the mistakes that tank each metric, and how to check your own site free in 30 seconds.

---

If you've searched for "good Core Web Vitals score" you've probably already found the
three numbers: LCP under 2.5 seconds, INP under 200 milliseconds, CLS under 0.1. Those
are correct, but they're also the least useful part of the answer, because passing them
requires understanding what Google is actually measuring and where — which is where
most sites get tripped up.

### The three metrics, and what "good" actually means

**Largest Contentful Paint (LCP)** measures how long it takes the largest visible
element — usually a hero image, a background image, or a block of text — to render.
Google's thresholds:

- **Good:** ≤ 2.5s
- **Needs improvement:** 2.5s–4.0s
- **Poor:** > 4.0s

**Interaction to Next Paint (INP)** replaced First Input Delay (FID) as the
responsiveness metric. It measures the latency of *every* interaction over the page's
lifetime — not just the first one — and reports something close to the worst case.
Thresholds:

- **Good:** ≤ 200ms
- **Needs improvement:** 200ms–500ms
- **Poor:** > 500ms

**Cumulative Layout Shift (CLS)** measures unexpected layout movement — content
jumping around as images, ads, fonts, or injected elements load in.

- **Good:** ≤ 0.1
- **Needs improvement:** 0.1–0.25
- **Poor:** > 0.25

"Good" for the page as a whole means all three metrics are individually in the
"Good" bucket for at least 75% of page loads (the 75th percentile), not on average.
This is the detail that catches people out: a site with a median LCP of 1.8s can still
fail the CWV assessment if its 75th-percentile LCP — the slower quarter of real visits,
often on weaker connections or devices — sits above 2.5s.

### Field data vs. lab data — you're being graded on the former

This is the single biggest source of confusion. There are two kinds of Core Web
Vitals data:

- **Field data (real-user monitoring / CrUX):** actual measurements from real Chrome
  users visiting your site over the past 28 days, aggregated by Google's Chrome UX
  Report. This is what Search Console's Core Web Vitals report shows you, and it's
  what (indirectly) factors into ranking.
- **Lab data:** a single simulated run — what Lighthouse, PageSpeed Insights' "lab"
  section, or most one-off analyzer tools give you.

A page can score 100 in a Lighthouse lab run and still be "Poor" in the field, because
lab data runs once, on a fast simulated connection, with no other tabs open, no ad
blockers, and no real user rage-clicking a button five times while a script blocks
the main thread. If your site doesn't have enough traffic for CrUX to report field
data at all (a common situation for smaller sites), Search Console falls back to
"origin-level" data from your whole domain, which can be misleadingly generous or
punishing depending on what your other pages look like. When in doubt, trust field
data over lab data, and treat lab data as a debugging tool, not a scorecard.

### Where each metric actually goes wrong

**LCP problems** are almost always one of: the LCP image isn't preloaded and gets
discovered late (browser has to parse CSS/JS before it finds the image URL); the image
is unnecessarily large in bytes; a web font blocks the text from painting
(`font-display: block` or a bad preload); or server response time (TTFB) alone eats
most of the 2.5-second budget before the browser has even started downloading
anything. Preload the LCP image with `fetchpriority="high"`, serve it in a modern
format (AVIF/WebP) at the right dimensions, and audit TTFB before touching anything
else in the frontend.

**INP problems** come from long JavaScript tasks blocking the main thread when a user
clicks, taps, or types — huge bundles that need parsing/executing, unoptimized event
handlers, third-party scripts (chat widgets, analytics, ad tech) doing synchronous
work on interaction, or React/Vue re-renders that touch far more of the DOM than the
interaction warranted. Breaking up long tasks (`scheduler.yield()`, chunking work),
auditing third-party scripts for what they do on click/input, and avoiding
unnecessary re-renders on interaction are the highest-leverage fixes.

**CLS problems** are almost always: images or embeds without explicit `width`/`height`
(or `aspect-ratio`) reserving their space before they load; web fonts causing a
visible reflow between the fallback and final font (FOUT) when line-height or
character width differs meaningfully; ads or consent banners injected above existing
content instead of into reserved space; or content inserted dynamically (a "you might
also like" block, a notification bar) above the fold after initial render. Reserve
space for everything that loads asynchronously, and pick a fallback font with similar
metrics to your web font (or use `size-adjust` in a `@font-face` block) to shrink the
FOUT jump.

### Why your own numbers might disagree with a tool's numbers

Different tools test from different locations, on different simulated connection
speeds, with different device profiles, and — critically — some report lab data only
while others pull field/CrUX data when available. If PageSpeed Insights says your LCP
is "Poor" but a competitor's tool says "Good," check which kind of data each one is
actually showing before assuming either is wrong.
