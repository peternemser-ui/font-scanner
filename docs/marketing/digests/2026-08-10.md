## Draft guide: What is a good Core Web Vitals score in 2026?

**Suggested title tag:** What Is a Good Core Web Vitals Score in 2026? (LCP, INP, CLS Explained) | Site Mechanic
**Suggested meta description:** The current LCP, INP, and CLS thresholds for a "good" Core Web Vitals score in 2026, what Google actually does with the data, and how to check where your site stands in under a minute.

---

If you've searched for "what is a good Core Web Vitals score," you've probably already found ten articles that all say the same three numbers and move on. This one's going to explain what those numbers actually mean, where they come from, and — more usefully — what to do when your site misses them, because that's the part most guides skip.

### The three metrics, and the thresholds that matter

Core Web Vitals are three metrics Google uses as a proxy for real-world page experience:

- **LCP (Largest Contentful Paint)** — how long until the largest visible element (usually a hero image, a big heading, or a video poster) finishes rendering. **Good: 2.5 seconds or less.** Needs improvement: 2.5–4s. Poor: over 4s.
- **INP (Interaction to Next Paint)** — how long the browser takes to visually respond after a user clicks, taps, or types. **Good: 200 milliseconds or less.** Needs improvement: 200–500ms. Poor: over 500ms. INP replaced First Input Delay (FID) as the official interactivity metric in March 2024, and it's a stricter test — FID only measured the delay before the browser started processing an interaction; INP measures the full round trip through to the next frame being painted, including run-on JavaScript. Sites that passed FID comfortably sometimes fail INP for the first time.
- **CLS (Cumulative Layout Shift)** — how much visible content unexpectedly moves while the page is loading or after it's loaded. **Good: 0.1 or less.** Needs improvement: 0.1–0.25. Poor: over 0.25. This one's a unitless score, not a time — it's the sum of how far elements moved, weighted by how much of the viewport they occupy.

To pass Core Web Vitals as a page (not just get individual "good" scores), Google requires the **75th percentile** of real visits to be in the "good" range for all three metrics simultaneously. That 75th-percentile detail matters more than most guides let on — it means one in four of your real visitors can have a rough experience and you still technically "pass." It also means your fastest test run on your fastest machine tells you almost nothing; only field data across real visitors reflects the actual score.

### Where the data comes from — and why your Lighthouse score doesn't match

This is the single most common point of confusion: Lighthouse (and PageSpeed Insights' "Diagnostics" tab) gives you **lab data** — one simulated run, on a fixed device profile, on a fixed network throttle. The Core Web Vitals report in Search Console, and the score that actually affects ranking, comes from **field data** — the Chrome UX Report (CrUX), aggregated from real Chrome users who visited your page with telemetry enabled, over a rolling 28-day window.

These can diverge a lot. A page can score green in Lighthouse and still fail its real Core Web Vitals if your actual visitors are disproportionately on older phones, slower connections, or in regions with higher latency to your server — none of which a single lab run captures. If you only ever check Lighthouse, you're checking a proxy for a proxy.

The practical implication: don't chase a single Lighthouse number to zero. Fix root causes (see below), then confirm the fix using field data — either your own Real User Monitoring, or by waiting for CrUX to reflect it (typically a 28-day lag before Search Console fully catches up).

### What actually moves each metric

**LCP** is almost always one of: an unoptimized hero image (serve modern formats — WebP/AVIF — and size it correctly, don't let the browser downscale a 4000px image in CSS), a render-blocking web font swap, or a slow server response (Time to First Byte) pushing everything else back. Preload your LCP image with `<link rel="preload" fetchpriority="high">`, and check whether your CDN/hosting TTFB is over ~600ms — if so, that's often the real bottleneck, not the frontend.

**INP** usually traces back to long JavaScript tasks blocking the main thread when a user interacts — third-party scripts (chat widgets, analytics, ad tags) are frequent offenders because they're outside your direct control but still block your thread. Break up long tasks, defer non-critical third-party scripts until after first interaction, and avoid heavy work inside event handlers (a click handler that triggers a big re-render is a classic INP killer).

**CLS** is almost always missing dimensions: images and embeds without explicit `width`/`height` (or `aspect-ratio` in CSS) that shift content down once they load, web fonts swapping to a different-metric fallback font without `font-display` tuning or a matched fallback via `size-adjust`, or content injected above existing content (cookie banners, promo bars) without reserving space first.

### Mobile and desktop are scored separately — and mobile is usually worse

Search Console reports Core Web Vitals as two separate groups, mobile and desktop, and it's common for a site to pass comfortably on desktop while failing on mobile. This isn't a coincidence: mobile CrUX data reflects a much wider spread of device capability (a five-year-old Android phone on a patchy connection reports data alongside a current-generation flagship on wifi), and Google's own guidance is to treat mobile as the priority since it's usually both the larger share of traffic and the harder bar to clear. If you're only checking one, check mobile — and if a tool only gives you a single blended score without breaking out device type, treat that score with some suspicion, because it can hide a mobile-specific problem entirely.

It's also worth checking Core Web Vitals per template, not just per URL. A single product page passing doesn't tell you anything about your checkout flow, your blog, or your homepage — each tends to have a different LCP element and different third-party script load, so they fail independently. Search Console groups pages into buckets by similarity, which helps, but spot-checking your highest-traffic templates individually (homepage, a representative product/article page, checkout) catches issues the aggregate view can smooth over.

### How often to re-check

Because the score is a rolling 28-day field-data average, changes don't show up immediately — ship a fix today and Search Console's official number won't fully reflect it for up to four weeks. That lag is exactly why a fast, on-demand lab check matters even though it isn't the "real" score: it tells you within seconds whether a fix actually addressed the root cause (smaller image, fewer render-blocking requests, reserved space for that ad slot) before you commit to a month-long wait to find out from field data. Use lab tools to iterate quickly, then use Search Console field data as the final confirmation once enough time has passed.

### A realistic target, not a perfect one

"Good" per Google's thresholds is the bar for not being penalized — it is not, on its own, a competitive advantage anymore, because enough sites now clear it that it's table stakes rather than a differentiator. The sites that actually benefit from Core Web Vitals work are the ones currently failing one or more metrics; going from "poor" to "good" tends to show up clearly in bounce rate and conversion, while going from "good" to "excellent" (well under the thresholds) has much smaller, harder-to-measure returns. Prioritize accordingly — fix the metric you're failing before you polish the ones you're already passing.

### Check where you actually stand

Lab data from a single run won't tell you the truth, and Search Console's field data can lag by weeks and only covers pages with enough traffic to have CrUX data at all. If you want an immediate LCP/INP/CLS read on a specific page — including which images, scripts, or elements are actually responsible for a metric missing its target — run it through [Site Mechanic's Core Web Vitals analyzer](https://sitemechanic.io/core-web-vitals.html).
