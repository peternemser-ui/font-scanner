**1. [How can I quickly identify the font used on a webpage using JavaScript?](https://stackoverflow.com/questions/79999849/how-can-i-quickly-identify-the-font-used-on-a-webpage-using-javascript)** — Stack Overflow, posted 2026-09-01, currently 0 answers (closed as duplicate, but the duplicate target doesn't actually cover the fallback-stack problem the asker raised).

Summary: A developer building a small "inspect this element's typography" utility wants font-family, size, weight, line-height, and color via JS, and specifically doesn't know how to handle a `font-family` value that's a fallback stack rather than the one font actually rendering.

Drafted reply:
> `getComputedStyle(el).fontFamily` will give you the whole stack (e.g. `"Inter, -apple-system, sans-serif"`), not which one the browser actually picked — that's the part people usually get stuck on.
>
> Two ways to resolve it to the *actual* rendered font:
> - `document.fonts.check("16px " + family)` for each name in the stack, in order — the first one that returns `true` is the one being used (this is what `document.fonts` was built for, and it's the most reliable native option).
> - The old canvas-measurement trick (render the same string in the target font vs. a known-absent font and compare pixel widths) still works as a fallback for browsers where `document.fonts` isn't populated yet at call time, but you shouldn't need it in anything shipping today.
>
> For the rest: `fontSize`, `fontWeight`, `lineHeight`, and `color` all come straight off the same `getComputedStyle()` call, no extra work needed — just be aware `lineHeight` can come back as `"normal"` if it's not explicitly set, so you may want to fall back to `fontSize * 1.2` in that case for display purposes.
>
> (Disclosure: I built a full-page version of this — [Site Mechanic's font analyzer](https://sitemechanic.io/enhanced-fonts.html) — for exactly this fallback-resolution problem, scanning every element on a page instead of just one. `document.fonts.check()` is the core trick either way.)

**2. [Does a CSS-only `<details>`/`<summary>` disclosure widget need `aria-expanded` for accessibility?](https://stackoverflow.com/questions/79983981/does-a-css-only-details-summary-disclosure-widget-need-aria-expanded-for-acc)** — Stack Overflow, posted 2026-07-22, 1 existing answer, still gets traffic (WCAG 2.1 4.1.2 question, evergreen).

Summary: Asker uses native `<details>`/`<summary>` for a disclosure widget and wants to know whether they still need to hand-manage `aria-expanded`, and whether that's possible without JS.

Drafted reply:
> No — and this is a common thing to over-engineer. Native `<details>`/`<summary>` already exposes the expanded/collapsed state through the accessibility tree via the `open` attribute; browsers map that to the equivalent of `aria-expanded` for you automatically in the accessibility API, and screen readers announce "expanded"/"collapsed" from that native semantic. Adding your own `aria-expanded` on top is redundant at best, and a bug risk at worst — if your CSS/JS state and the native `open` attribute ever drift apart (which is easy to do with a CSS-only approach driven by something other than the `open` attribute itself), you'll end up with an ARIA attribute that contradicts what the browser is actually reporting, which is worse than not having it at all.
>
> `aria-expanded` only becomes something *you* need to maintain when you're building a *fake* disclosure widget out of a plain `<div>`/`role="button"` instead of the native element — at that point you've opted out of the free semantics and have to reimplement them by hand, including keyboard handling.
>
> Short version: keep using native `<details>`/`<summary>`, don't add `aria-expanded`, and you're WCAG 4.1.2-compliant by construction. If you want a second opinion beyond manual testing, an automated pass (axe, WAVE, or [Site Mechanic's accessibility scanner](https://sitemechanic.io/accessibility-analyzer.html)) will flag it if you ever do end up with a conflicting manual `aria-expanded`.

**3. [In an HTML table, what's the use of the `scope` attribute for `<tr>`, `<th>`, and `<td>`?](https://stackoverflow.com/questions/79991445/in-an-html-table-whats-the-use-of-the-scope-attribute-for-tr-tg-and-td)** — Stack Overflow, posted 2026-08-07, 1 existing answer, low-traffic but a genuinely common confusion point.

Summary: Asker read that `scope` on `<th>` matters for accessibility but doesn't understand what "relates to" actually means in practice.

Drafted reply:
> Think of `scope` as telling a screen reader *which header to re-announce* when the user's cursor moves to a given data cell. Without it, a screen reader can usually still guess correctly for simple grids by position, but it breaks down fast on anything with merged cells, multi-row headers, or an irregular layout — the browser has no other way to know "this `<th>` is the header for this whole column" versus "for this one row."
>
> `scope="col"` on a `<th>` means: every `<td>` below it, in the same column, is described by this header.
> `scope="row"` means: every `<td>` to the right of it, in the same row, is described by this header.
>
> Concretely — a screen reader user tabbing through a pricing table cell by cell will hear something like "Pro plan, $29" instead of just "$29," because `scope` told it which header applies. Without `scope`, that context is silently missing for exactly the users who need it most; sighted users never notice because the visual table layout already tells them which header a cell belongs to.
>
> `scope` isn't valid on `<tr>` or `<td>` at all — it's a `<th>`-only attribute, which might be the source of confusion in the MDN wording. If you have a table with both row and column headers, you'd put `scope="col"` on the top row's `<th>`s and `scope="row"` on the left column's `<th>`s.

**4. [How do I configure a Content-Security-Policy for Meta Pixel's use of `properties://` URIs?](https://stackoverflow.com/questions/79996801/how-do-i-configure-a-content-security-policy-for-meta-pixels-use-of-properties-uris)** — Stack Overflow, posted 2026-08-20, 1 existing answer, unresolved as of last check.

Summary: Asker sees CSP `connect-src` violations logged against a non-standard `properties://` scheme coming from Meta Pixel's own script, and can't find an allow-rule that stops the console errors.

Drafted reply:
> This is a known quirk of the Pixel's internal signal-batching code, not something wrong with your policy — `properties://` isn't a real network scheme the browser is trying to reach externally, it's an internal pseudo-URI Meta's script uses to tag telemetry payloads before routing them through its actual (already-CSP-legitimate) `connect.facebook.net` calls. Chrome's CSP reporting doesn't know that and reports it as a blocked `connect-src` attempt anyway.
>
> You generally can't "fix" it with an allow-rule — `connect-src properties:` isn't a valid scheme match in most browsers' CSP implementations, and even where it parses, you'd be opening a hole for a scheme that offers no real security boundary since nothing can actually route traffic through it. Most people either live with the harmless console/report noise or, if it's tripping up a `report-uri`/`report-to` pipeline with false positives, filter that specific `blocked-uri: properties` pattern out at the reporting endpoint rather than in the policy itself.
>
> Worth double-checking with whatever's actually leaving your server: paste your live CSP header (not the one you think you're sending) into [Google's CSP Evaluator](https://csp-evaluator.withgoogle.com/) or a header inspector — proxies, CDNs, and meta-tag/header conflicts are a more common source of "my CSP isn't doing what I wrote" than this particular Pixel noise. (Site Mechanic's [security header scanner](https://sitemechanic.io/security-analyzer.html) will show you the CSP as actually served, header by header, if you want a second read on it.)

## Draft guide: What is a good Core Web Vitals score in 2026?

**Suggested title tag:** `What Is a Good Core Web Vitals Score in 2026? (LCP, INP, CLS Thresholds)`
**Suggested meta description:** `The actual Google thresholds for LCP, INP, and CLS in 2026 — what "good" means, why your Lighthouse score and your Search Console report disagree, and how to check your real numbers.`

---

If you've searched for this, you've probably already seen the numbers: Largest Contentful Paint (LCP) under 2.5 seconds, Interaction to Next Paint (INP) under 200 milliseconds, Cumulative Layout Shift (CLS) under 0.1. Those are correct. They're also not the whole story, and the parts that get left out are exactly the parts that cause the most confusion — like why your Lighthouse score says 98 while Search Console tells you you're failing Core Web Vitals for real users.

This is the practical version: what the numbers mean, where they come from, why two "correct" tools can disagree, and what to actually do about it.

### The three metrics, briefly

**LCP (Largest Contentful Paint)** measures how long it takes the largest visible content element — usually a hero image, a big block of text, or a background image — to render. Good: under 2.5s. Needs improvement: 2.5s–4s. Poor: over 4s. It's a proxy for "does this page feel like it loaded."

**INP (Interaction to Next Paint)** replaced First Input Delay (FID) as the third Core Web Vital in March 2024, and by now it's the one catching people off guard, because it measures something FID didn't: the full cost of *every* interaction during a page visit, not just the first one, and it measures the whole round trip — input, processing, and the next paint — not just the delay before your event handler starts running. Good: under 200ms. Needs improvement: 200ms–500ms. Poor: over 500ms. A page can pass FID comfortably and still fail INP if the fifth click on the page, after some client-side state has piled up, takes 600ms to respond.

**CLS (Cumulative Layout Shift)** measures unexpected visual movement — content jumping around as things load in. Good: under 0.1. Needs improvement: 0.1–0.25. Poor: over 0.25. It's unitless by design: it's a product of how much of the viewport moved and how far, summed across the whole session (with a windowing mechanism that groups shifts into "session windows" so a single scroll-triggered burst doesn't get double-counted across separate incidents).

### Why "good" is a percentile, not a score

Here's the part that trips people up: Google's pass/fail bar for search ranking purposes isn't based on your best run, your average run, or a lab test at all — it's the **75th percentile of real visits**, per metric, using data from the Chrome User Experience Report (CrUX), which only includes sites with enough Chrome traffic to produce a statistically meaningful sample. To "pass" Core Web Vitals as a ranking signal, 75% of your real, measured page loads need to be good on LCP, 75% on INP, and 75% on CLS — as separate thresholds, not averaged together. A site that's fast for most visitors but has a slow tail (say, a subset on old Android devices, or a specific page template) can fail the field assessment while looking fine on any individual lab test.

This is why Lighthouse and Search Console disagree so often. Lighthouse runs a **lab test**: one simulated page load, one device profile, one network throttle setting, no real user variance. It's reproducible and great for debugging, but it's a single synthetic data point. Search Console's Core Web Vitals report uses **field data** — real CrUX numbers from real visitors, aggregated over the trailing 28 days. A page can lab-test at LCP 1.8s on a fast connection in a data center and field-test at LCP 3.9s because half your actual traffic is on mid-range phones on cellular networks in markets with real latency. Neither number is wrong. They're measuring different things.

If your site doesn't get enough Chrome traffic to appear in CrUX at all (common for smaller sites, or specific low-traffic pages), Search Console won't have field data for it, and Google falls back to origin-level aggregation or, in its absence, effectively can't apply the field signal to that URL — which is its own trap, because it means you can't fully verify your real-world standing without either meaningful traffic or your own Real User Monitoring.

### What actually moves these numbers

For **LCP**: find the actual LCP element first (Lighthouse and Chrome DevTools' Performance panel both name it) — optimizing images across the whole page when the LCP element is your hero video's poster frame is wasted effort. Common fixes: preload the LCP resource specifically (not everything — over-preloading creates contention that can make LCP worse), serve responsive image sizes instead of one oversized master, and eliminate render-blocking CSS/JS that delays the browser from even starting to paint.

For **INP**: this is almost always about JavaScript execution cost, not network time. Look for long tasks (anything blocking the main thread for more than 50ms) that run during or right after user interaction — third-party scripts (chat widgets, analytics, ad tags) are frequent culprits because they're outside your direct control but still block your main thread. Breaking up long tasks with `scheduler.yield()` or manual chunking, deferring non-critical JS, and auditing what your tag manager is actually loading synchronously are the highest-leverage fixes.

For **CLS**: almost always missing dimensions. Explicit `width`/`height` (or `aspect-ratio` in CSS) on images and embeds so the browser reserves space before the asset loads; reserving space for ads and dynamically injected content instead of letting it push the layout down after render; and being careful with web fonts — a FOUT (flash of unstyled text) swap from a fallback font to a custom one with different metrics can shift layout by itself if you haven't size-adjusted the fallback.

### The check-it-yourself version

Lab tools (Lighthouse, PageSpeed Insights' lab section, WebPageTest) are for debugging a specific page in detail. Field tools (Search Console, CrUX directly, or your own RUM) are for knowing where you actually stand with real users — check both, and don't trust a single lab run as your final answer, since lab results vary run to run with system load and network conditions. If you want a fast gut-check across LCP, INP, and CLS together with plain-language flags on what's actually causing each one, [run your site through Site Mechanic's Core Web Vitals analyzer](https://sitemechanic.io/core-web-vitals.html) — it's free, takes about 30 seconds, and doesn't require a signup.
