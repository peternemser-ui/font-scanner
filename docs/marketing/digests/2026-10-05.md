### What Is a Good Core Web Vitals Score in 2026?

If you've ever opened PageSpeed Insights and gotten a wall of green, yellow, and red
without knowing which numbers actually matter, you're not alone. Core Web Vitals have
been part of Google's ranking signals since 2021, and the thresholds themselves haven't
moved much — what's changed is how seriously they're enforced in practice, how the
tooling reports them, and which metric actually breaks on most real sites. Here's the
current, accurate picture.

#### The three metrics, and the actual thresholds

Core Web Vitals is three separate metrics, each measuring something different, each
with its own "good" cutoff:

- **LCP (Largest Contentful Paint)** — how long it takes the largest visible element
  (usually a hero image, a heading, or a banner) to render. **Good: under 2.5 seconds.**
  Needs improvement: 2.5–4s. Poor: over 4s.
- **INP (Interaction to Next Paint)** — how long the page takes to visibly respond
  after a click, tap, or keypress, measured across the whole page visit and reported
  at a high percentile (not an average). **Good: under 200ms.** Needs improvement:
  200–500ms. Poor: over 500ms. INP replaced FID (First Input Delay) as the official
  responsiveness metric in March 2024 — if you're still looking at FID numbers, you're
  looking at a retired metric.
- **CLS (Cumulative Layout Shift)** — how much visible content jumps around during
  load, scored as a unitless number based on how much of the viewport moved and how
  far. **Good: 0.1 or lower.** Needs improvement: 0.1–0.25. Poor: over 0.25.

A page "passes" Core Web Vitals only when all three are in the "good" range — not on
average, but at the 75th percentile of real visits. That last part trips people up
constantly: your Lighthouse score in DevTools is a single lab run on your machine,
on your connection. Google's actual ranking signal comes from CrUX (the Chrome User
Experience Report), which aggregates real visitor data over a rolling 28 days. A site
can look perfect in a local Lighthouse run and still fail Core Web Vitals in Search
Console, because real users on real networks and real phones have a worse 75th
percentile than a clean lab test.

#### Why INP is the one that actually breaks

Of the three, LCP and CLS are comparatively easy to fix once and mostly forget:
preload your hero image, set explicit width/height on images and embeds, reserve
space for ads and fonts, and both metrics usually land comfortably in "good." INP is
different — it's not a one-time fix, because it's measuring every interaction across
the full lifetime of a page visit, not just the initial load.

The usual INP killers:
- **Heavy JavaScript execution on the main thread** — anything that blocks the thread
  for more than 50ms delays the next paint, regardless of what triggered it.
- **Large third-party scripts** — analytics, chat widgets, ad tech, and A/B testing
  tools are frequent offenders because they run code you don't control, often on
  every interaction.
- **Unoptimized event handlers** — a click handler that triggers a full re-render of
  a large component tree, or that does synchronous work (like a heavy DOM query)
  before yielding control back to the browser.
- **Input handling during hydration** — common in client-rendered frameworks, where a
  user interacts with a page before the JavaScript has finished hydrating it, and the
  interaction queues behind a large hydration task.

Fixing INP usually means breaking up long tasks with `requestIdleCallback` or
`scheduler.yield()`, auditing third-party scripts for ones that genuinely don't need
to run on every page, and lazy-loading non-critical JavaScript so the main thread has
room to respond to real user input instead of your own initialization code.

#### Does a Core Web Vitals pass actually move rankings?

Google has been consistent on this: Core Web Vitals are one of many ranking signals,
and they mostly act as a tiebreaker between pages with comparable content quality and
relevance — they won't rescue thin or poorly-matched content, and they won't bury
genuinely better content over a few hundred milliseconds of LCP. Where they matter
most in practice is user behavior, not the algorithm directly: a page with a 4-second
LCP or a layout that jumps while someone's trying to tap a button loses visitors
before they ever see what you built, and that shows up in bounce rate and conversion
long before it shows up in a ranking change.

#### Fields vs. lab, and why both numbers can disagree

Two tools, two different numbers, same page — this is normal, not a bug:

- **Lab data** (Lighthouse, PageSpeed Insights' "Diagnostics" section, Chrome DevTools)
  runs a synthetic test under fixed, throttled conditions. It's reproducible and great
  for debugging a specific issue, but it's one run, not a population.
- **Field data** (CrUX, Search Console's Core Web Vitals report, PageSpeed Insights'
  top section) aggregates real visits over the last 28 days. It's what Google actually
  uses for ranking, but it lags — a fix you ship today won't show up in CrUX for
  roughly a month, and low-traffic pages may not have enough real visits to get scored
  at all ("Not enough data").

If you only check one, check field data for "are we actually passing," and lab data
for "why, specifically, is this page failing."
