> exactly that first pass — no signup, ~30 seconds. If you genuinely need a signed ACR (a real
> VPAT, not just a self-assessment), the ITI VPAT template is free and some accessibility
> consultants will do a scoped, cheaper review for OSS/nonprofit projects if you ask directly —
> worth a few cold emails before assuming full-price is the only option.

## Draft guide: What Is a Good Core Web Vitals Score in 2026?

Next in the Tier 2 priority order (seo-content-plan.md) — this is guide #1 of that list, and no
prior digest means none of the six guides have been drafted yet.

**Suggested title tag:** Good Core Web Vitals Score 2026: LCP, INP & CLS Thresholds Explained
**Suggested meta description:** What counts as a "good" Core Web Vitals score in 2026? Real
thresholds for LCP, INP, and CLS, how Google actually uses them, and how to check your own site
free.

---

If you've searched for this, you've probably already seen the number. Google's official
"good" thresholds for Core Web Vitals have not changed since INP replaced FID in March 2024,
and they're still what Search Console, PageSpeed Insights, and every third-party checker
grade against in 2026:

| Metric | Good | Needs Improvement | Poor |
|---|---|---|---|
| **LCP** (Largest Contentful Paint) | ≤ 2.5s | 2.5s – 4.0s | > 4.0s |
| **INP** (Interaction to Next Paint) | ≤ 200ms | 200ms – 500ms | > 500ms |
| **CLS** (Cumulative Layout Shift) | ≤ 0.1 | 0.1 – 0.25 | > 0.25 |

That table is the whole "answer" most guides stop at. The more useful question is what those
numbers actually mean for your site, and where people get the interpretation wrong.

### The threshold that matters is the 75th percentile, not your last test run

Google doesn't grade Core Web Vitals on a single Lighthouse run. The Chrome User Experience
Report (CrUX) — the data source behind Search Console's Core Web Vitals report — aggregates
real visits over a rolling 28-day window and grades your site on the **75th percentile** of
real users, split by mobile and desktop.

That distinction explains almost every "but my Lighthouse score was 98!" complaint. Lighthouse
runs in a lab: one device profile, one throttled network, no real-world variance. CrUX is field
data from actual visitors on their actual phones, on their actual 4G connections, in their actual
countries. A site can be "good" in Lighthouse and "needs improvement" in Search Console at the
same time — both numbers are correct, they're just measuring different things. If you only have
one number to trust for SEO purposes, trust the field data.

### Why INP is the metric everyone still gets wrong

INP replaced First Input Delay (FID) as the responsiveness metric in March 2024, and a lot of
"how to fix your web vitals" content still hasn't caught up. FID only measured the delay before
the *first* interaction started processing. INP measures the full round trip — input delay,
processing time, and paint — for every interaction during the page's lifetime, and reports the
worst (or near-worst) one.

That means a single heavy click handler buried three interactions into a session — a filter
dropdown, an "add to cart" button, a modal close — can tank your INP even if the initial page
load felt instant. Common causes worth checking first:

- Third-party scripts (chat widgets, analytics, ad tech) hogging the main thread during a click
- Large JavaScript bundles that block interaction processing until they finish parsing
- Heavy re-renders on state changes in React/Vue apps — updating far more DOM than the
  interaction actually changed
- `setTimeout`/microtask chains that delay the visual update after processing finishes

The fix is almost never "add more caching." It's profiling the actual interaction in Chrome
DevTools' Performance panel and finding what's running during that specific click.

### CLS: still mostly an images-and-fonts problem

Cumulative Layout Shift hasn't gotten more forgiving, and the most common causes in 2026 are
the same as they were in 2021:

- Images and embeds without explicit `width`/`height` (or `aspect-ratio` in CSS)
- Web fonts that swap in with a different width than the fallback, shifting text around —
  this is exactly what `font-display: optional` or matched fallback metrics are for
- Ads, embeds, or cookie banners injected after initial render without reserved space
- Content that shifts in response to network responses (a "recommended products" row that
  pops in below the fold and pushes everything down)

Font-related CLS is worth calling out specifically because it's invisible in a quick eyeball
test — the page "looks fine," but the layout shift score is measuring milliseconds of movement
most people don't consciously notice.

### What "good" actually buys you

Core Web Vitals are one signal among many in Google's ranking systems — not a guaranteed
ranking boost, and Google has said as much repeatedly. What's better documented is the
correlation with conversion and engagement: sites that fix LCP and INP problems consistently
see lower bounce and better session metrics, because slow and janky pages are simply worse to
use. Treat Core Web Vitals as a user-experience investment that happens to have SEO upside,
not an SEO hack that happens to improve UX. That framing keeps you from over-optimizing one
number (like chasing a 0.0 CLS) at the expense of the actual page.

### Checking your own numbers

Search Console's Core Web Vitals report is the source of truth for how Google sees your site,
but it only updates every 28 days and only shows enough traffic to have CrUX data at all — new
or low-traffic pages often show nothing. For a same-day read using the same LCP/INP/CLS
thresholds above, plus a full breakdown of what's driving each number, run a scan with
[Site Mechanic's Core Web Vitals analyzer](https://sitemechanic.io/core-web-vitals.html) — it's
free, takes about 30 seconds, and doesn't require an account. If you want a second opinion on
lab data specifically, [PageSpeed Insights](https://pagespeed.web.dev/) blends Lighthouse and
CrUX in one report and is worth cross-checking against.
