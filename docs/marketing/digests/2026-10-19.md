## Draft guide: What is a good Core Web Vitals score in 2026?

**Suggested title tag:** What Is a Good Core Web Vitals Score in 2026? (LCP, INP, CLS Thresholds)
**Suggested meta description:** The actual LCP, INP, and CLS thresholds Google uses in 2026, what "75th percentile" means in practice, and why your Lighthouse score and your Search Console report can legitimately disagree.

---

If you've ever gotten a green Lighthouse score and a red Core Web Vitals warning in
Search Console for the same page, you're not imagining it — they're measuring different
things, and only one of them is what Google actually uses for ranking.

### The three metrics, as of 2026

Core Web Vitals is three metrics, not one score:

- **LCP (Largest Contentful Paint)** — time until the largest visible element (usually a
  hero image, a big block of text, or a video poster frame) finishes rendering. Good:
  under 2.5s. Needs improvement: 2.5s–4s. Poor: over 4s.
- **INP (Interaction to Next Paint)** — replaced FID as the responsiveness metric back
  in March 2024. It measures the latency of *every* interaction on the page over its
  lifetime (clicks, taps, key presses) and reports a high percentile, not just the first
  one. Good: under 200ms. Needs improvement: 200ms–500ms. Poor: over 500ms.
- **CLS (Cumulative Layout Shift)** — a unitless score summing how much visible content
  moves around unexpectedly during the page's lifetime. Good: under 0.1. Needs
  improvement: 0.1–0.25. Poor: over 0.25.

If you remember one thing from this list: FID is gone. If a tool, a course, or a
consultant is still talking about First Input Delay as a ranking signal, it's at least
two years out of date.

### "Good" means the 75th percentile, not your best run

This is the part that trips people up. A "good" Core Web Vitals score isn't a single
number from a single page load — it's **at least 75% of real visits to a page or origin
hitting the "good" threshold**, measured over a rolling 28-day window of actual Chrome
users (this is the Chrome UX Report, or CrUX). That has two consequences worth
internalizing:

1. **You can't "pass" Core Web Vitals in a lab tool.** PageSpeed Insights, Lighthouse,
   and Site Mechanic's own scan all run a *simulated* page load on *one* connection
   profile, once. That's useful for diagnosing what's slow, but it is not the same
   measurement Google uses for the ranking signal. Only real-user field data (CrUX),
   aggregated in Search Console or the CrUX API, tells you if you're actually passing.
2. **Low-traffic pages may have no CrUX data at all.** Google needs a meaningful sample
   size before it'll report field data for a URL. If your page gets Google Search
   Console tells you "data is not available" instead of pass/fail, that's not a bug —
   it's a traffic floor.

This is also why your lab score and your field score can legitimately disagree, and why
two runs of the same lab tool 30 seconds apart can give different LCP numbers: network
jitter, CPU throttling simulation, and even which CDN edge node answered the request all
move the result. Lighthouse explicitly throttles CPU and network to simulate a
mid-tier mobile device, which is deliberately pessimistic compared to what a desktop
visitor on fiber experiences — and CrUX blends every real device and connection a
visitor actually used, mobile and desktop both, unless you filter it.

### What actually moves each metric

**For LCP:**
- Find the actual LCP element first — don't guess. It's usually a hero image, but on
  text-heavy pages it can be a `<h1>` or a block of body copy if a web font swap delays
  it.
- Preload the LCP image (`<link rel="preload" as="image">`) and make sure it isn't
  `loading="lazy"` — lazy-loading your own hero image is the single most common
  self-inflicted LCP regression.
- Cut server response time (TTFB). No amount of front-end optimization fixes a page
  that takes 1.5s to start streaming from the server.
- Serve properly sized, modern-format images (WebP/AVIF) — don't ship a 4000px source
  image and let CSS scale it down in the browser.

**For INP:**
- Break up long JavaScript tasks. INP penalizes any single task over 50ms blocking the
  main thread when an interaction happens — this is almost always third-party scripts
  (chat widgets, analytics, ad tech) or a large unoptimized bundle, not your own render
  logic.
- Defer non-critical JS and use `requestIdleCallback` or scheduler APIs for low-priority
  work.
- Avoid synchronous layout thrashing in event handlers — reading `offsetHeight` right
  after a DOM write forces a reflow inside the interaction's critical path.

**For CLS:**
- Set explicit `width`/`height` (or `aspect-ratio`) on every image and embed, including
  ads and iframes.
- Reserve space for web fonts with `font-display: optional` or a matched fallback font
  via `size-adjust`, so text doesn't reflow when the custom font finishes loading.
- Never inject content above existing content unless it's in response to a user
  interaction (a banner that pushes the page down 0.4s after load is a CLS violation
  even if the user never notices it).

### The honest caveat

No automated tool — ours included — can hand you a Core Web Vitals verdict from a
single scan, because the metric is defined over real traffic. What a scan *can* do is
simulate a load, point at the specific element or script causing each metric to slip,
and give you something concrete to fix before your real-user data catches up. Treat the
lab score as a todo list, and Search Console's field report as the grade.
