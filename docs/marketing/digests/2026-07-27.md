### What Is a Good Core Web Vitals Score in 2026?

If you've searched this question, you've probably already seen the numbers: LCP under 2.5 seconds, INP under 200 milliseconds, CLS under 0.1. Those thresholds are correct and haven't changed since INP replaced FID as the third Core Web Vital in March 2024. But "good score" is doing a lot of hidden work in that sentence, and most of the confusion developers run into comes from what those numbers don't tell you.

#### The three metrics, briefly

- **LCP (Largest Contentful Paint)** — time until the largest visible element (usually a hero image, banner, or heading block) finishes rendering. Good: ≤2.5s. Needs improvement: 2.5–4s. Poor: >4s.
- **INP (Interaction to Next Paint)** — the worst-case delay between a user interaction (click, tap, keypress) and the next frame painting in response. Good: ≤200ms. Needs improvement: 200–500ms. Poor: >500ms. Unlike its predecessor FID, INP measures the *full* interaction, not just input delay — this is why sites that "passed" under FID sometimes fail under INP.
- **CLS (Cumulative Layout Shift)** — a unitless score summing up unexpected layout movement during the page's lifespan. Good: ≤0.1. Needs improvement: 0.1–0.25. Poor: >0.25.

A page "passes" Core Web Vitals when it's in the "good" band for all three, at the 75th percentile of real visits.

#### The part everyone skips: the 75th percentile of *field* data

This is the single biggest source of confusion. Google doesn't grade your Core Web Vitals off a Lighthouse run — it grades off the **Chrome User Experience Report (CrUX)**, which is real, anonymized field data from actual Chrome users visiting your site over a rolling 28-day window. Your page needs 75% of those real visits to land in the "good" band, not your best run in a dev tool.

That means:

1. **A single Lighthouse or PageSpeed Insights score is a lab estimate**, run on one simulated device and connection profile, once. It's useful for catching regressions locally and in CI, but it is not what Search Console's Core Web Vitals report — or Google's ranking systems — actually use.
2. **If your site doesn't have enough traffic to populate CrUX**, Search Console falls back to origin-level (whole-domain) data or shows no data at all for that URL. Low-traffic sites and pages behind auth are often flying blind on the "official" numbers, which is exactly when a lab tool becomes your only signal.
3. **Field and lab scores can legitimately disagree** — a fast dev laptop over broadband will out-perform whatever mix of phones and connections your real 75th-percentile visitor has. If PageSpeed Insights says "good" but Search Console says "needs improvement," the field number is the one that matters for search, and the gap is telling you something real about your actual traffic mix (older devices, slower networks, more third-party scripts loading in the wild than in your test run).

#### Does failing Core Web Vitals actually hurt rankings?

Core Web Vitals are one signal among many in Google's page experience system, and Google has been consistent that content relevance dominates. In practice: failing badly (poor LCP/INP on a content-heavy page competing in a tight niche) can be a tiebreaker against you; failing narrowly on CLS while your content is excellent rarely tanks rankings on its own. Treat CWV as a floor to clear, not a ceiling to optimize toward at the expense of everything else. It affects indexing eligibility for some experiences (e.g., AMP-adjacent surfaces historically) less than it affects raw user experience and conversion — a 1-second LCP improvement typically moves bounce rate and conversion more than it moves search position.

#### Common causes, by metric

**Bad LCP:** slow server response (TTFB), render-blocking CSS/JS above the fold, unoptimized/unlazy hero images, web fonts blocking text render (see: `font-display`), client-side-rendered content that doesn't paint until JS hydrates.

**Bad INP:** long JavaScript tasks blocking the main thread during interaction (heavy event handlers, large re-renders in React/Vue on every keystroke), too much third-party script (chat widgets, analytics, ad tech) competing for the main thread, layout thrashing inside click handlers.

**Bad CLS:** images and ads without explicit `width`/`height` (or `aspect-ratio`), web fonts swapping in at a different size/metrics than the fallback, content injected above existing content (cookie banners, "sign up" bars) after initial paint, animations that shift geometry instead of using `transform`.

#### Fixing the fastest wins first

If you only have an afternoon: set explicit dimensions on every image and ad slot (CLS), add `font-display: swap` plus a size-matched fallback font stack (CLS + LCP), defer or lazy-load anything below the fold that isn't the LCP element, and audit third-party scripts for anything you can remove or move to `async`/`defer` (INP). These four changes cover the majority of "needs improvement" sites we see.

#### Check where you actually stand

Lab tools and the official Search Console report both have blind spots — lab data doesn't reflect your real traffic mix, and CrUX needs 28 days and enough volume to populate at all, so it's useless for "did my fix work?" the day you ship it. A live one-off check (like [Site Mechanic's Core Web Vitals analyzer](https://sitemechanic.io/core-web-vitals.html)) sits in between: real Chrome rendering of the current version of your page, no signup, ~30 seconds, so you can verify a fix immediately instead of waiting a month for CrUX to catch up — as part of a full site scan that also covers SEO, accessibility, security headers, and typography in the same run.
