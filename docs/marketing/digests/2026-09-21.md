## Draft guide: Core Web Vitals in 2026: What's a Good LCP, INP & CLS Score

**Suggested title tag:** Core Web Vitals in 2026: What's a Good LCP, INP & CLS Score
**Suggested meta description:** The real thresholds for LCP, INP and CLS in 2026, why your Lighthouse score can disagree with Search Console, and how to check where your site actually stands.

---

If you've ever had Lighthouse tell you your page is fast while Google
Search Console's Core Web Vitals report says otherwise, you're not
misconfiguring anything — you're looking at two genuinely different
measurements. This guide covers what "good" actually means for each metric
in 2026, why the two numbers disagree, and what to check first when a page
fails.

### The three metrics, and the thresholds that matter

Core Web Vitals is three metrics, each with a "Good" / "Needs Improvement" /
"Poor" band:

- **LCP (Largest Contentful Paint)** — time until the largest visible
  element (usually a hero image, a banner, or a block of text) has
  rendered. Good: ≤2.5s. Needs improvement: 2.5-4s. Poor: >4s.
- **INP (Interaction to Next Paint)** — how long the page takes to visually
  respond to a user's interaction (click, tap, key press), measured across
  the whole page visit, not just the first interaction. Good: ≤200ms.
  Needs improvement: 200-500ms. Poor: >500ms.
- **CLS (Cumulative Layout Shift)** — how much visible content jumps around
  as the page loads (images without dimensions, late-injected banners,
  web fonts swapping in). Good: ≤0.1. Needs improvement: 0.1-0.25. Poor:
  >0.25.

One thing worth knowing if you learned Core Web Vitals a few years ago: INP
replaced FID (First Input Delay) as the responsiveness metric in March
2024. FID only measured the delay before the *first* interaction started
processing; INP measures the full visual response time across every
interaction on the page, which is a much harder bar to clear if you have
any heavy interaction handlers. If your team is still optimizing for FID,
that's the first thing to fix — it's a stale target.

### Why your Lighthouse score and Search Console disagree

This is the single most common point of confusion for developers, and it's
worth being explicit about because the two tools are measuring different
things entirely:

- **Lab data** (Lighthouse, PageSpeed Insights' "Diagnostics" section, most
  browser DevTools panels) is a single simulated page load on a controlled
  connection and device profile. It's reproducible and great for debugging
  a specific regression, but it's one data point.
- **Field data** (Chrome User Experience Report / CrUX, which is what
  Search Console's Core Web Vitals report and PageSpeed Insights' "Field
  Data" section both pull from) is real measurements from real Chrome
  users who actually visited your site, aggregated over a rolling 28-day
  window, scored at the **75th percentile**.

The 75th-percentile part matters: your page is scored "Good" only if 75%
of real visits met the threshold. That means a page that's fast for most
users but has a long tail of slow sessions — visitors on old Android
phones, congested wifi, throttled connections — can fail Core Web Vitals
in Search Console while looking perfectly fine in a Lighthouse run from a
fast office connection. A recent industry study from Calibre found this
pattern across airline websites specifically: sites that likely test fine
in a local dev environment but fail badly once you weight in the real
mix of devices and networks their actual customers use.

Practical takeaway: always check field data before trusting a lab score.
If CrUX doesn't have enough traffic data for your URL yet (common for
newer or lower-traffic pages), Search Console falls back to an
origin-level aggregate across your whole domain — which can also produce
a confusing mismatch if your homepage is fast but a template used by
hundreds of product pages isn't.

### What usually breaks each metric

**LCP failures**, in rough order of how often they show up:
1. The hero image isn't preloaded and isn't using a modern format (AVIF/
   WebP) — this alone frequently accounts for a full second or more.
2. Render-blocking CSS or synchronous third-party scripts delay the whole
   paint, including text.
3. The LCP element is a web font that hasn't loaded yet — see the CLS
   section below, the two are related.
4. Slow server response time (TTFB) pushes everything downstream later,
   including LCP, even if the front-end is otherwise fine.

**INP failures**, in rough order:
1. Long JavaScript tasks that block the main thread — third-party tag
   managers and analytics scripts are frequent offenders because they're
   easy to add and rarely profiled afterward.
2. Heavy event handlers doing synchronous work (large DOM updates, layout
   thrashing) directly in a click/input handler instead of deferring with
   `requestIdleCallback` or breaking the work into smaller chunks.
3. Large, unoptimized React/Vue component trees re-rendering more than
   necessary on every interaction.

**CLS failures**, in rough order:
1. Images and embeds without explicit `width`/`height` (or `aspect-ratio`
   in CSS), so the browser can't reserve space before the asset loads.
2. Web fonts that swap in with a different width/x-height than the
   fallback, shifting text — `font-display: optional` or matching
   fallback metrics avoids this.
3. Ads, cookie banners, or other content injected above existing content
   after the initial layout is already painted.

### Monitoring over time, not just once

A single scan is a snapshot — useful for catching an obvious regression,
but Core Web Vitals field data is a rolling 28-day window, so a fix you
ship today won't be reflected in Search Console for weeks. A few habits
that make this less painful:

- **Re-check after every deploy that touches the homepage or a high-traffic
  template**, not just when something looks broken. Regressions from a new
  third-party script or an unoptimized image are easy to miss until the
  field data catches up and it's too late to correlate the cause with a
  specific release.
- **Watch URL groups, not just your homepage.** Search Console groups
  similar URLs (e.g. all product pages on an e-commerce site) and reports
  on the group. A template-level fix or regression will show up there
  before it shows up on any single page you happen to check by hand.
- **Don't chase a perfect lab score.** Once field data is in the "Good"
  band at the 75th percentile, further lab-score optimization has
  diminishing returns for ranking purposes — Google's ranking signal uses
  the field data, not your Lighthouse number.

### What "good" realistically looks like in 2026

There's no universal passing score — Google evaluates Core Web Vitals per
URL (or per URL group, for templated pages), not per site. A marketing
site built on static HTML with a handful of optimized images can hit all
three "Good" thresholds without much effort. A JavaScript-heavy dashboard
app with a lot of client-side interactivity has to work much harder for
INP specifically, because every interaction is measured, not just the
initial load.

The realistic bar to aim for: all three metrics in the "Good" band for at
least 75% of real visits, checked against field data, not a single lab
run. If you're currently relying on Lighthouse alone, that's the gap
worth closing first — it's a five-minute check and it changes which
problem you should actually be working on.
